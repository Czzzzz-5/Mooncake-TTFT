# 实验卡：v1 验证（SLOT_MB=192）—— A/B 对照

日期：2026-09-16　操作人：wuzichun

## 改了什么

采用 **A/B 对照**设计，而不是拿旧基线比新数据（旧基线 406.63ms 是带第三方
负载时测的，不可比）。同一台安静机器、同一 seed 777，唯一变量是
`MC_TCP_GPU_STAGING` 开关：

- **A 组（基线重测）**：`MC_TCP_GPU_STAGING=0`，强制走 legacy 路径
  （每 64KB new + 同步 cudaMemcpy + delete）
- **B 组（v1）**：`MC_TCP_GPU_STAGING_SLOT_MB=192, SLOTS=4`（锁页池全开）

## 环境

- 机器负载：**全机安静**。实验前 13:21 快照：GPU0/1/2 全空（2MiB），
  无其他用户登录（who 为空），CPU top 全为本人无关痛痒进程。
- GPU 状态：三块 5090 正常，GPU0 驱动问题已恢复（可用、空闲）。
- 流程：清场（杀干净旧进程+确认端口释放）→ A 组 → 全杀 → B 组重启。

## 生效证据（对照清单）

- [x] 两端日志均有 `GpuStagingPool: 4 x 201326592 bytes pinned slots ready`
      （**正面证据**：池真实初始化，见 `results/raw/B_pool_init.txt`）
- [x] 无 `exceeds slot capacity` / `all slots busy` WARNING（未回退）
- [x] `pulling kv_caches finished` 计数 = 5（warmup+4），`failed transfers/recv = 0`
- [x] xfer time 147 → 114ms，TTFT 427 → 352ms，方向与幅度符合 v1 理论（消除
      pageable 税 + 单次拷贝，但拷贝/发送仍串行）

## 结论

- **v1 真实生效**。这次收益有据可查，不是 09-15 那种归因存疑的数字。
- **TTFT 收益：−75ms（全 4 请求均值）/ −50ms（去 req0）**，约 −12~18%。
- **观察**：xfer 114ms 仍高于理论 ~60ms——拷贝完再发的串行性还在，
  正是 v2 多槽流水的靶子；另注意到 TTFT 呈 ~300/~400 双模交替，
  疑似多请求并发时槽竞争或 lane 调度效应，v2 设计时需关注。
- **下一步**：开工 v2 多槽流水（拷贝‖发送），目标 ~30ms 档。
  可选：seed 888 复跑两组加固结论。
