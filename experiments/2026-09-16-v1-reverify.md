# 实验卡：v1 验证（SLOT_MB=192）—— 三轮 A/B 对照

日期：2026-09-16　操作人：wuzichun（数据命令由本人手动执行）

## 设计

**三轮 A/B 对照**，每轮：同一台安静机器、同一 seed，唯一变量是
`MC_TCP_GPU_STAGING` 开关。不拿旧基线（406.63ms，含第三方负载）参与对比。

- **A 组**：`MC_TCP_GPU_STAGING=0`，legacy 路径（1760 次同步小拷贝）
- **B 组**：`MC_TCP_GPU_STAGING_SLOT_MB=192, SLOTS=4`，锁页池全开

## 环境

- 每轮开始前清场（杀旧进程、确认端口/GPU 释放）；14:00-14:45 期间整机安静
  （无其他用户登录，GPU 无外人任务）。
- GPU0 驱动问题已恢复，三块 5090 正常。

## 解剖：TTFT 里到底有什么（2026-09-17 修正版，epoch 校准 + 7 点插桩）

**方法**：在 `mooncake_connector.py` 加 7 个 `[XDBG]` epoch-ns 打点
（D_SEND_PULL / P_RECV_PULL / P_WAIT_WAKEUP / P_READY / P_SEND_EXEC /
P_REQ_FINISHED / P_POST_RECORD），用 D 侧内部一致性定标 perf_counter→epoch
偏移，逐请求复原时间轴（脚本：`scripts/dissect_epoch.py`，原始档
`results/raw/X2_*`）。

**⚠️ 重大修正：上一版"~190ms 传输前常数项"是定标伪影，不存在。**
旧分析用 `P_REQ_FINISHED(epoch) ↔ first_token(perf)` 定标，但
`request_finished` 在 KV 发送完成后才触发，比 first_token 晚 ~149ms，
导致 P 侧偏移被整体抬高 ~149ms，"P 端请求完成得晚"的假象就是这么来的。
正确定标（D 侧 `req_queued → D_SEND_PULL` 间隙仅 0.2ms，且程序序
queued 必在 pull 前）为 1789386860334.9ms；佐证：D_SEND_PULL→P_RECV_PULL
ZMQ 耗时 0.8ms，双端 epoch 一致。

**修正后的瀑布（X2 轮，seed123，客户端口径 avg 328ms）**：

| 段 | 耗时 | 说明 |
|---|---|---|
| proxy → 双端引擎入队 | **~1ms** | 与旧版"传输前常数项"相容的部分其实是误会 |
| 入队 → prefill 开算 | 4.5~8.5ms | P 引擎调度派发 |
| prefill 计算 | 9.5~11.3ms | model_forward，16K 字符 prompt |
| **首 token → D 调度上 KV** | **~200ms（快档）/ ~280ms（慢档）** | 含 GPU→staging 拷贝、Mooncake TCP 传输（~50MB）、传输完成检测、D 调度反应；**全场最大头** |
| decode 首步 forward | ~10ms | |
| D 首 token → 客户端首包 | **34~49ms** | detokenize + SSE 流水线，第二目标 |
| 客户端 TTFT 合计 | 288~372ms | 与逐段加总吻合 ✓ |

**双模交替确认**：快/慢档按请求到达序奇偶交替（68/150/73/145ms），
与客户端 ~300/~410ms 双模一一对应。交替源在"首token→D调度"窗口内，
嫌疑：传输完成→唤醒 D 调度器的路径（而非传输本身）。

**新发现（顺手挖出的坑）**：`GpuStagingPool` 是**懒初始化**——首个
GPU 路径传输才触发 4×192MB 锁页分配，实测 **386ms**（13:32:45.487
pull 到达 → 45.874 slots ready）。目前只打在 warmup 上，但应在
connector 初始化时预建。

**旧版"确凿结论"表弃用**：其中 took（57~143ms）来自日志行解析，
被上述窗口定义混淆；xfer time 引擎指标口径仍待修。

## 结论

- **v1 真实生效，收益 −40~−75ms（三轮回平均 −54ms / −13%）**，焊死。
- 收益构成：传输自身变快（消除 pageable 税 + 单次拷贝）+ 不再用
  legacy 默认流同步拷贝切碎并发 prefill 计算（连带收益）。
- **下一步（按优先级，2026-09-17 解剖后修订）**：
  1. **拆 "首token→D调度" ~200/280ms 窗口**：在 D 侧加 epoch 打点
     （KV recv 完成时刻、调度器被唤醒时刻），分离出 TCP 传输净耗时 vs
     传输完成检测/调度反应耗时；同时查清快/慢档按奇偶交替的机制
     （嫌疑：完成→唤醒路径，或传输 lane 交替）。
  2. **砍 D 首 token → 客户端首包 34~49ms**：查 detokenizer/SSE 流水线
     是否有固定轮询间隔。
  3. **GpuStagingPool 预建**：把 386ms 懒初始化挪到 connector 初始化
     （一次性修复，避免去掉 warmup 后第一笔真实请求吃全额惩罚）。
  4. v2 多槽流水（针对 1 中分离出的传输净耗时）。
- 遗留：① xfer time 引擎指标口径需修；② `cudaStreamPerThread` 隐患未验证；
  ③ `mooncake_tcp_bench.py --buf gpu` 立纯净传输层标尺（辅助 1）。
