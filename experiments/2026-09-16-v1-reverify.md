# 实验卡：v1 验证（SLOT_MB=192）—— 三轮 A/B 对照

日期：2026-09-16　操作人：wuzichun（数据命令由本人手动执行）

## 设计

**三轮 A/B 对照**，每轮：同一台安静机器、同一 seed，唯一变量是
`MC_TCP_GPU_STAGING` 开关。不拿旧基线（406.63ms，含第三方负载）参与对比。

- **A 组**：`MC_TCP_GPU_STAGING=0`，legacy 路径（1760 次同步小拷贝）
- **B 组**：`MC_TCP_GPU_STAGING_SLOT_MB=192, SLOTS=4`，锁页池全开

## 环境

- 每轮开始前清场（杀旧进程、确认端口/GPU 释放）；14:00-14:45 期间整机安静
  （无其他用户登录，GPU 无外人任务）。
- GPU0 驱动问题已恢复，三块 5090 正常。

## 解剖：250ms 里到底有什么（2026-09-17，源码 + 日志拆段）

**方法**：读 vLLM 调度器/MooncakeConnector 源码确认事件语义，再用 [TTFT]
事件 + 引擎日志锚点对 B3/A3 两组日志做时间轴复原（脚本：
`scripts/dissect_waterfall.py`）。

**确凿结论**：

| 段 | 耗时 | 证据 |
|---|---|---|
| 调度→执行（引擎内派发） | **~2ms** | 修正：此前 110~160ms 是分析脚本 bug（取了最后一个 execute 事件） |
| 引擎步频（等待期轮询） | ~2ms/步 | 每请求 122~170 条 WAITING 轮询日志 → 步边界延迟 ≤4ms |
| 发起 pull → ZMQ → P 就绪 | ≤10ms | 日志行紧贴 queued |
| **数据传输净耗时 took** | **B 组 57~59ms 与 140~143ms 交替；A 组 93~227ms** | P 侧 `Sending to done, took Xs` |
| 传输完成→scheduled | ≤4ms | 步边界 |

**两个重要修正/发现**：

1. **双模交替的真凶找到了**：v1 传输净耗时在 ~58ms 和 ~142ms 两档之间交替
   （A 组 legacy 是 93~227ms 乱值）。TTFT 双模由 took 双模直接驱动。
2. **剩下 ~190ms 常数项未解**：250ms 窗口 − took(59~143) − 已确知的 ≤15ms
   ≈ **190ms 的"传输前开销"，与 took 无关、每笔都在**。源码层面排除了：
   调度步频（2ms）、D 端 pull 发起（≤10ms）、P 端等 prefill（P 算完只要
   ~15-38ms，早于 pull 到达）、ZMQ 阻塞收包（无轮询 sleep）。
   嫌疑人集中在：P 侧 ready 事件的跨线程唤醒、`sender_loop` 线程池排队、
   每请求新建 ZMQ DEALER 连接的握手成本。**需插桩实测定位**。

## 结论

- **v1 真实生效，收益 −40~−75ms（三轮回平均 −54ms / −13%）**，焊死。
- 收益构成：传输自身变快（消除 pageable 税 + 单次拷贝）+ 不再用
  legacy 默认流同步拷贝切碎并发 prefill 计算（连带收益）。
- **下一步（按优先级）**：
  1. **插桩解剖 ~190ms 常数项**（最大单笔收益来源）：在 mooncake_connector.py
     的 pull 发起 / P 端 ready / executor 提交 / write 返回 四点加
     perf_counter 打点，一轮实验即可定位。
  2. **解释并消除 took 双模（58 vs 142ms）**：疑似 lane/连接状态交替，
     与 v2 的多 lane 流水设计强相关。
  3. v2 多槽流水（took 段 57~142ms → 目标 ~30ms）。
- 遗留：① xfer time 指标口径需修；② `cudaStreamPerThread` 隐患未验证；
  ③ `mooncake_tcp_bench.py --buf gpu` 立纯净传输层标尺（辅助 2）。
